# CR350: Osprey OTS strings through an AM16/32

Status: **compiled and checked with offline protocol fixtures; hardware validation pending**.
Last checked: 2026-10-05. Target: CR350, AM16/32 in 4x16 mode, OTS Modbus RTU.
Example: [CR350_OTS_MultiCh.CRB](../../Campbell%20Scientific/CR350_OTS_MultiCh.CRB).

## Configure an installation

Edit the `USER CONFIGURATION` section, compile for CR350, and send the program
using PC400 or LoggerNet. The supplied names and counts are illustrative.

| Setting | Meaning | Default |
| --- | --- | --- |
| `MEAS_INTERVAL_MIN` | Whole minutes between scheduled sweeps | 15 |
| `NUM_CHANNELS` | Highest physical mux channel used, including gaps; 1..16 | 4 |
| `MAX_SENSORS` | Allocated capacity per channel; at least the largest count | 10 |
| `ArrayName(ConfigCh)` | Label in the matching `Case` inside `ConfigureChannels` | Array01, Array02, Unused03, Array04 |
| `SensorCount(ConfigCh)` | Number of sensors on that physical channel | 3, 2, 0, 4 |

For example, to use only channel 16, set `NUM_CHANNELS=16`, set counts for channels
1..15 to zero, and edit `Case 16`. Cases above `NUM_CHANNELS` are ignored. A count
of zero skips polling; the mux still advances through that channel.

Counts must be between zero and `MAX_SENSORS`, and no greater than 247. Capacity
must be 1..247; the protocol limit is not a guarantee of logger memory, electrical
capacity, or acceptable sweep duration. Compile the actual dimensions before
deployment. Keep `MAX_SENSORS` close to the installed maximum to conserve storage.
Names allow 19 ASCII characters plus a terminating null in `String * 20`.

Configuration is loaded from the source at every program start. Public names and
counts can be edited for commissioning, but those edits are not persistent.
Each sweep snapshots them before polling and records that snapshot. Put final
settings in the source. Changing dimensions changes the table schema; retain
existing logger data before deploying a program with different dimensions.

## Wiring and sensor prerequisites

Reuse the proven ASP installation wiring. The following identifies signal
functions, not a new assignment of the mux common-bank terminals.

| Connection | Function |
| --- | --- |
| CR350 C1 to mux RES | Enable/reset |
| CR350 C2 to mux CLK | Advance one physical channel |
| CR350 COM2 RX through mux to blue | Osprey RS-485 A |
| CR350 COM2 TX through mux to white | Osprey RS-485 B |
| Array supply through mux to red | 12 V array power |
| Array return through mux to black | Ground |

The existing mux power supply and control ground remain connected as before.
All four array conductors are switched together in 4x16 mode. Disabling RES
disconnects the selected array. This program relies on that switched-power
arrangement for a fresh boot; it does not drive a CR350 SW12 output.

Prepare each string with:

- Unique sequential aliases **1..N**, nearest to farthest, restarting at 1 on
  each mux channel. The program neither discovers nor assigns addresses.
- **9600 baud, 8 data bits, no parity, one stop bit**.
- **`measure_on_boot=1`** and **`broadcast_on_wake=0`**. The inspected firmware
  has additional baud/sleep behavior after startup broadcasting, so broadcasting
  must be disabled for this polling example.
- A firmware build with the register map below. Record its version and the
  installed filter/integration and sleep settings during commissioning.

The program reads sensors without writing configuration or triggering additional
measurements. `SerialOpen(...,0,0,256,4)` uses format 0 for 8N1 and communication
mode 4 for transparent half-duplex RS-485. The two options have different roles.

## Acquisition, timing, and power

At startup the program fills the Public readings without writing `OTS_Data`.
Scheduled scans then acquire and store one sweep each, using the same interval
constant for `Scan` and `DataInterval`. The startup sweep is followed by the next
scheduled scan; it does not establish a new schedule relative to its finish.

Each sweep clears old data, captures configuration, measures logger health, and
holds RES and CLK low. After at least one second with all arrays disconnected,
it enables the mux, clocks channels in order, waits for each enabled string to
boot, flushes the serial input, and polls aliases 1..N. It disconnects the mux at
the end, including when global configuration is rejected. Invalid and disabled
channels are clocked past and may be briefly connected, but are not polled.

Initial timing values, **requiring bench confirmation**:

| Parameter | Default |
| --- | --- |
| All-channel power-off/reset interval | 1000 ms |
| Mux pulse and subsequent settling delay | 10 ms each |
| Per-channel boot wait | `3500 + 550 * SensorCount` ms |
| Modbus attempts per sensor | 2 total attempts |
| Response timeout per attempt | 200 units of 0.01 seconds = 2 seconds |
| Delay after each sensor | 120 ms |

Boot timing depends on firmware, filter/integration settings, string size and
power conditions. The wait combines margin from the ASP example with the OTS CR6
example's per-sensor allowance; it is not a measured guarantee for this program.
Allow roughly four seconds plus the inter-sensor delay per unresponsive sensor
when budgeting two timeouts, in addition to boot, mux and processing overhead.

`SweepDuration_s` measures the complete routine, including reset, boot waits and
communications. `SweepOverrun=1` means that duration met or exceeded the configured
interval. Choose an interval with margin, including fault cases. This flag reports
the condition; it does not change the interval. Check the logger's skipped-scan
diagnostics too. Readings across sensors/channels are sequential, not synchronized.

## Wire format and decoding

Each sensor gets one FC3 request for **24 physical holding registers, 256..279**.
In Campbell's one-based API this is `Start=257, Length=24, ModbusOption=3` into
`RawRegisters(24) As Long`. Option 3 reads unsigned 16-bit values, one register
per array element. See [Campbell's ModbusClient reference](https://help.campbellsci.com/crbasic/cr1000x/Content/Instructions/modbusclient.htm).

The expected response contains 48 data bytes, or 53 bytes including Modbus framing
and CRC. Campbell's Modbus instruction handles the transaction and CRC; the program
decodes only a successful response. No ASCII fallback is used.

| Field | Physical registers, zero-based | Buffer indexes, one-based | Units/type |
| --- | --- | --- | --- |
| Unused leading registers | 256..257 | 1..2 | ignored |
| `OTS_V` | 258..259 | 3..4 | float32, V |
| `OTS_DegC` | 260..261 | 5..6 | float32, degrees C |
| `OTS_X` | 262..263 | 7..8 | float32, g |
| `OTS_Y` | 264..265 | 9..10 | float32, g |
| `OTS_Z` | 266..267 | 11..12 | float32, g |
| `OTS_Roll` | 268..269 | 13..14 | float32, radians |
| `OTS_Pitch` | 270..271 | 15..16 | float32, radians |
| `OTS_Yaw` | 272..273 | 17..18 | float32, radians |
| Unused intervening registers | 274..278 | 19..23 | ignored |
| `OTS_Status` | 279 | 24 | unsigned 16-bit integer |

The on-wire floats are IEEE-754 in ABCD order (high word first). The CR350 uses
little-endian numeric memory. `DecodeOTSFloat` copies the low word into destination
bytes 0..1 and the high word into bytes 2..3 with `MoveBytes`; there is no numeric
integer-to-float conversion. This helper specifically targets CR350 memory order.
See [CR350 Modbus programming](https://help.campbellsci.com/CR350/shared/communication/modbus/modbus-prog.htm)
and [MoveBytes](https://help.campbellsci.com/crbasic/cr1000x/Content/Instructions/movebytes.htm).

The firmware may perform another measurement after sending a Modbus reply,
depending on its settings. One block read keeps readings and status together in
one response. Reading each float separately can span different measurements.
The older OTS CR6 example also reads status with a float option; do not copy that
status transaction. Status occupies one 16-bit register, not two.

Angles retain the firmware's native 0..2*pi convention, with no baseline, axis
selection or degree conversion. Yaw is the firmware's gravity-derived third
rotation angle. This example does not measure magnetic compass heading.

## Data, status, and troubleshooting

`OTS_Data` contains logger health, sweep duration/overrun, `ConfigError`,
`SweepArrayName`, `SweepSensorCount`, `ChannelConfigError`, and all sensor arrays.
The two `Sweep...` metadata arrays are snapshots of the Public settings.
All measurements use IEEE4 storage; status/result/validity fields use Long.

Sensor array indexes always mean **(physical channel, sensor alias)**. The last
dimension varies fastest: (1,1)..(1,MAX_SENSORS), then channel 2, and so on.
Campbell expands these into output fields. Labels are metadata, not dynamically
generated column names; renaming an array does not change the field identities.
Every allocated slot is stored, including disabled channels and unused capacity.

| Diagnostic | Meaning |
| --- | --- |
| `ConfigError=0` | Configuration accepted |
| `ConfigError=1/2/3` | Invalid channel count / capacity / interval or timing; no polling |
| `ConfigError=4` | At least one channel has an invalid sensor count; other valid channels continue |
| `ChannelConfigError(ch)=1` | Count below zero, above allocated capacity, or above 247 |
| `OTS_ResultCode=-9999` | Local sentinel: this slot was not polled |
| `OTS_ResultCode=0` | Modbus response accepted |
| Other result codes | Campbell communication result; consult the ModbusClient reference |
| `OTS_Status=-1` | Local sentinel: no accepted response in this sweep |
| `OTS_Valid=1` | Accepted response AND sensor status zero |

Every float starts each sweep as NAN, every validity flag as zero. Failed
transactions are not decoded. Nonzero sensor status leaves the returned values
available for diagnosis, but validity remains zero. Use `OTS_Valid` when selecting
readings for downstream analysis; status zero is the sensor's own assessment,
not an independent calibration or plausibility check.

Firmware-reported status codes:

| Status | Meaning in the inspected OTS source |
| --- | --- |
| 0 | Measurement OK |
| 1 | Measuring / measurement did not complete successfully |
| 2 | Acceleration vector squared exceeds 1.21 (magnitude exceeds 1.1 g) |
| 3 | Zero acceleration vector, treated as an accelerometer error |
| 4 | Input voltage below 4 V |
| 5 | ADXL355 not responding |
| 6 | No measurement initialized since power-on |

Unknown status values are retained and marked invalid. These codes do not expose
every internal exception independently; the program preserves the reported code.

For no replies, check the physical mux channel, common wiring, A/B polarity,
aliases, 9600 baud and startup broadcasting first. For status 6, verify
`measure_on_boot` and allow enough boot time. For failures at the far end, verify
power and string continuity as well as timing. For unexpected angle values,
check units, firmware axis conventions and both diagnostics before changing the
decoder. A failure on one alias does not stop attempts at subsequent aliases.

## Verification and bench acceptance

Run the repeatable offline checks from the repository root:

```powershell
.\tools\Test-OTSExample.ps1
# Optional compiler location:
.\tools\Test-OTSExample.ps1 -Compiler 'C:\Campbellsci\Lib\Compilers\cr350comp.exe'
```

On 2026-10-05 these passed:

- Nine protocol fixtures, each containing all eight floats, with statuses 0..6,
  32768 and 65535. Fixtures include positive/negative numbers, positive/negative
  zero and nonzero low words. The checker extracts the actual byte-copy operations
  and register indexes from the CRBasic source and checks exact IEEE-754 bits.
- Nine CR350 compiler variants: default unequal/sparse counts; one sensor; only
  channel 16; exact allocated capacity; count above capacity; negative count;
  all channels disabled; one channel with address/capacity 247; one-minute interval.

Compiler variants and reports are retained in the temporary directory printed by
the script. They do not overwrite existing examples or create tracked build files.
The fixture checker models byte copies on the host; it does **not** execute CRBasic
on a logger. Compiling invalid-count variants confirms syntax only, not runtime
rejection. The 247-address compile does not establish a supported physical string
length. No sensor/logger firmware was changed or program uploaded during these
checks.

Complete these checks on hardware before calling the example validated:

1. Record CR350 OS, OTS firmware/configuration, mux mode, actual wiring, names,
   counts and timing. Compile the deployment configuration against that logger OS.
2. Start with a known stationary sensor on channel 1. Confirm all eight fields,
   status zero and validity one. Compare with the Python logger/raw response;
   its displayed voltage/temperature and angles are rounded, while this program
   stores the received float32 values. Check XYZ against the raw register payload.
3. Test unequal strings with an unused intermediate channel, then channel 16.
   Verify stored names/counts and physical channel/alias indexes match the wiring.
4. After a successful sweep, disconnect a sensor/string and repeat. Its former
   values must become NAN, status -1, result nonzero, validity zero; later aliases
   and channels must still be attempted.
5. Produce a known nonzero sensor status (for example, use a test sensor with
   measure-on-boot disabled to obtain status 6). Confirm the received values and
   status are retained but validity is zero. Restore the sensor configuration.
6. Test zero, negative, exactly-at-capacity and over-capacity counts. Invalid
   channels must report an error without polling or array overrun; valid channels
   must retain their original channel numbers. Test all channels disabled.
7. Observe RES/CLK and selected-array supply: deterministic reset, correct
   advancement, and array power removed after the sweep. Confirm a fresh boot on
   every selection and allow more off/boot time if the actual installation needs it.
8. Confirm startup fills Public values only; scheduled scans produce one table
   record each. Test one-minute and deployment intervals. Check sweep duration,
   overrun and skipped scans with healthy sensors and timeout failures.
